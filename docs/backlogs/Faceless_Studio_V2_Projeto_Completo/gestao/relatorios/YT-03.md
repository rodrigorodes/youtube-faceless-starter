# YT-03 — O provider bloqueia a publicação quando a autorização não resolve para o canal

**Data:** 2026-11-21
**Fatia:** YT-03 (gate de identidade no `RunPublication`/provider antes do upload)
**Base:** `f848a57` (`merge: o canal referencia o destino do YouTube + resolvedor de autorizacao (YT-02)`)

**Entregue:** sim — decisão pura, porta com a identidade do token, gate ligado no `RunPublication` e testes verdes.

## Objetivo

Ligar a **regra obrigatória** do desenho (§3): antes de publicar, o provider garante que a
autorização **resolve para o `youtubeChannelId` esperado**; a **divergência bloqueia o upload**.
Quando o canal do estúdio tem destino (`channel_profiles.youtube_channel_id`), o upload só acontece
se a autorização usada pertencer **exatamente** àquele canal do YouTube. Se o token/autorização for
de **outro** canal, **bloquear** (nada enviado, nada de sucesso simulado).

## O que foi feito (3 commits)

### 1. Decisão pura e testável — `160fc3a`

Em `domain/channel.py`, ao lado do resolvedor YT-02:

```python
def verify_publication_authorization(
    channel: ChannelProfile,
    authorizations: Iterable[ChannelAuthorization],
    *,
    token_channel_id: str | None,
) -> PublicationAuthorizationVerdict
```

Reusa `resolve_publication_authorization` (não duplica a resolução) e acrescenta a comparação com o
**canal a que o token de fato pertence**. Decisão `ALLOW`/`BLOCK` com motivo nomeado:

- canal **sem destino** (`youtube_channel_id is None`): **ALLOW** (preserva o caminho antigo);
- **sem** autorização `CONNECTED` para o destino: **BLOCK**;
- token de **outro** canal: **BLOCK** (motivo nomeia os dois canais);
- canal do token **desconhecido** (`None`): **BLOCK** — na dúvida sobre a identidade, não se publica
  (falha fechada). Puro: `domain` sem I/O nem import de adapter.

### 2. A porta diz a que canal o token pertence — `d15eccb`

`TokenProvider.execute(project_id)` passou de `-> str` para `-> AccessToken`:

```python
@dataclass(frozen=True)
class AccessToken:
    token: str = field(repr=False)          # o valor nunca entra em log
    youtube_channel_id: str | None = None
```

- `EnsureAccessToken` devolve o canal lido da **associação legada** do projeto
  (`YouTubeChannelRepository.get(project_id).channel_id`) — a identidade disponível hoje.
- `EnvRefreshTokenProvider` devolve `youtube_channel_id=None`: o refresh token do arquivo **não**
  passou por uma conferência de identidade; com destino, o gate falha fechado em vez de presumir.
- `MissingTokenProvider`/`FallbackTokenProvider` e `ReconcilePublication` atualizados para `.token`.
- **Nenhum adapter de OAuth novo**: reaproveita `EnsureAccessToken`/`token_env` já existentes.
- Todos os testes que usavam a porta foram ajustados no mesmo commit (nada quebrado).

### 3. Gate ligado no `RunPublication` — `654a9da`

No `execute`, **depois** de obter o token e **antes** de qualquer `self.uploads.upload`:

```python
blocked = self._authorization_gate(pub, project_id, access_token.youtube_channel_id)
if blocked is not None:
    return blocked
```

`_authorization_gate` descobre o canal do projeto → destino → resolve as autorizações do canal →
`verify_publication_authorization`. Bloqueio usa o caminho existente `self._blocked(pub, motivo)`
(dead-letter `PERMANENT`); **não** se chama o uploader. Injeção por `__init__` com default `None`:

```python
def __init__(self, …, channels: ChannelProfileRepository | None = None,
             authorizations: ChannelAuthorizationRepository | None = None)
```

Sem repositórios, o gate devolve `None` (não bloqueia). Wiring só em `composition.py`.

## Regra de preservação de comportamento (crítico)

Quando o canal **não** tem destino configurado (`youtube_channel_id is None`) — **o estado de hoje:
0 canais com destino no banco** — o comportamento é **exatamente o de hoje: não bloqueia**. Vale
também para `RunPublication` construído sem os repositórios (default `None`). Isso é o que evita
travar a operação atual: nenhum canal aponta destino até a UX (YT-04) existir, então a publicação
segue pelo caminho antigo por projeto, sem verificação de identidade. Só **com destino** a
verificação liga e pode bloquear. Os testes existentes de publicação continuam verdes **sem
alteração semântica** (confirmado: o duplo `Tokens()` antigo recebe `channel_id=None` e o gate não
atua).

## O que ficou de fora / limitações honestas

- **Não** religuei nem alterei o modelo antigo por projeto (`channel_youtube_channels`,
  `YouTubeChannelRepository`) nem a UX/painel; `rich.py` e o render intactos.
- **Reconciliação:** `ReconcilePublication` foi adaptado à nova porta (`.token`) mas **não** recebe o
  gate de identidade — o gate date é o caminho de publicação (`RunPublication`), conforme o escopo.
- **Canal do token no caminho real:** o `EnsureAccessToken` usa a associação legada do projeto
  (`youtube_channels.project_id.channel_id`) como "canal do token". Quando a YT-04 criar as
  autorizações por canal, a política de "qual grant preferir" (ex.: mais recentemente validada)
  continua aberta (o resolvedor devolve a primeira `CONNECTED` na ordem do repositório).
- **Fallback de ambiente:** devolve canal `None`; com destino configurado, bloqueia (falha fechada).
  Não foi adicionado `channels.list` no fallback para não inventar identidade nem nova chamada.
- Ordem no `execute`: obtém-se o token e só então o gate decide. Se não houver autorização vigente,
  o refresh pode ter ocorrido antes do bloqueio — correção preservada, um desperdício mínimo que
  some quando a YT-04 popular as autorizações.
- Não toquei no checkout principal, nem reiniciei app (8000)/bridge (8787). Sem `git push`, merge ou
  `git add -A` (commits com caminhos exatos). Árvore limpa.
